# MC-simulator reliability vs rollout budget (analysis-only reuse of vineppo_replication rollouts)

## Question

In ~/vineppo_replication, the "simulator" value estimator is a k-rollout Monte-Carlo mean of
binary outcomes. How does its reliability scale with rollout budget k in {1, 2, 4, 8}, pooled and
within-problem (difficulty removed), and what is the implied compute-value tradeoff?

## Data

`~/vineppo_replication/results/data.jsonl` (read-only): 23 GSM8K problems x 3 prefixes = 69
prefixes. Per prefix the full run saved v_gold (fraction of 12 rollouts correct) and v_sim
(fraction of 6 disjoint rollouts correct) — verified against `full_run.log` (V* values are
multiples of 1/12, sim of 1/6; the README's 16/8 are the script defaults, NOT what this run used —
documentation bug worth fixing). Gold and sim rollouts are generated by the identical procedure
(same policy Qwen2.5-1.5B-Instruct-4bit, temperature 0.8, prompt, parser; `run.py:rollout_value`),
so per prefix we have 18 exchangeable Bernoulli outcomes whose success count
s_i = round(12*v_gold) + round(6*v_sim) is a sufficient statistic. Subsampling k outcomes without
replacement from this pool is therefore exactly equivalent to subsampling the raw saved rollout
outcomes. No new generation; analysis runs in ~22 s on CPU.

## Pre-registered method (this section was written before the analysis ran)

For each budget k in {1, 2, 4, 8} and each Monte-Carlo draw: for every prefix, randomly permute
its 18 outcomes; the estimator is the mean of the first k, the reference is the mean of the next
10 (disjoint; reference size fixed at m = 10 for all k so the target does not change across the
curve). Reliability r(k) = Pearson correlation across the 69 prefixes between estimator and
reference, averaged over B = 1000 draws (seed 0). Two versions:

- **pooled**: raw values (known to be dominated by between-problem difficulty, ICC ~ 0.88);
- **within-problem**: both estimator and reference centered by their problem mean (3 prefixes per
  problem) before correlating — the credit-assignment-relevant number per the repo's own README.

**CIs**: two-level bootstrap — resample the 23 problems with replacement (cluster bootstrap,
1000 replicates, seed 1), 20 fresh subsample draws averaged inside each replicate; percentile
95% CIs. CIs therefore reflect both problem-sampling and rollout-subsampling noise.

**Pre-stated primary test**: paired cluster-bootstrap 95% CI for r_within(8) - r_within(1).

**Primary quantitative claim**: the noise-to-signal ratio lambda in the binomial-reliability model
rho(k) = sqrt(k / (k + lambda)) (correlation of a k-rollout mean with the TRUE success
probability; lambda = E[p(1-p)] / Var(p) = rollouts needed to reach rho^2 = 0.5). Estimated two
ways: (a) moment-based from the 18-rollout counts, (b) one-parameter least-squares fit of
r(k) = rho(k) * rho(10) to the four empirical points. Reported for pooled and within-problem.

**Compute-value tradeoff**: cost per rollout from the original run log (242,127 generated tokens
over 1,716 continuations => ~141 tokens/rollout, ~2.8 s/rollout at 51 tok/s on the M4).

## Results (all numbers in results.json; figure reliability_curve.png)

| k | tokens | sec (M4) | r pooled [95% CI] | r within-problem [95% CI] | model rho vs truth (pooled / within) |
|---|---|---|---|---|---|
| 1 | 141 | 2.8 | 0.644 [0.509, 0.756] | 0.261 [0.093, 0.423] | 0.681 / 0.348 |
| 2 | 282 | 5.5 | 0.754 [0.630, 0.845] | 0.350 [0.136, 0.524] | 0.796 / 0.465 |
| 4 | 564 | 11.1 | 0.835 [0.736, 0.898] | 0.455 [0.210, 0.637] | 0.881 / 0.597 |
| 8 | 1129 | 22.1 | 0.887 [0.808, 0.931] | 0.558 [0.290, 0.727] | 0.935 / 0.725 |

**Primary test**: r_within(8) - r_within(1) = 0.297, paired cluster-bootstrap 95% CI
[0.156, 0.365] — excludes 0. (Pooled: 0.243 [0.174, 0.305].) As pre-stated, monotonicity was
expected; the informative result is the lambda split below.

**Lambda (rollouts needed for R^2 = 0.5 against true value):**
- pooled: lambda = 1.15 (moment) [95% CI 0.67, 2.06]; LSQ fit 1.15 — the two independent
  estimates agree, and the model curve fits all four empirical points (see figure).
- within-problem: lambda = 7.36 (moment) [95% CI 3.61, 25.71]; LSQ fit 7.23.

**Interpretation / compute-value tradeoff.** The pooled and within-problem signals live on very
different budget scales. Problem difficulty is almost free: one 141-token rollout already gives
r = 0.64 against a 10-rollout reference (model: R^2 = 0.46 of true value), and the marginal
pooled R^2 per rollout collapses from 0.46 (1st) to 0.016 (8th) — diminishing returns after
k ~ 2. Step-level credit assignment (within-problem) is ~6x more expensive: lambda ~ 7 means
roughly 7 rollouts (~1000 tokens, ~20 s) are needed to explain half the variance of true
step-level value, and value accrues near-linearly across the whole k = 1..8 range
(marginal within R^2 per rollout: 0.121 at k=1, still 0.033 at k=8). Notably, the original run's
simulator (k_sim = 6) sat almost exactly at the within-problem half-saturation point.

**Sanity check**: the pipeline reproduces the repo's saved-aggregate correlation
(6-rollout sim vs 12-rollout gold) at r = 0.878, identical to the README's headline 0.878.

**Post-hoc items** (labeled per pre-registration): the marginal-R^2-per-rollout table is derived
from the fitted model, not directly estimated; the tokens/rollout figure treats screening/rank
continuations as the same average length as main-phase continuations.

## Caveats

- Reliability, not accuracy: the "truth" in rho(k) is the k -> infinity limit of the same policy's
  own rollouts (same temperature, prompt, parser). This quantifies rollout-budget noise only and
  inherits the circularity the repo's README already flags; it cannot speak to correctness
  against an external ground truth.
- Small clustered sample: 69 prefixes in 23 problems (3 per problem). Within-problem CIs are wide
  (r_within(8): [0.29, 0.73]; lambda_within CI up to 25.7) because within-problem true-value
  variance is small (0.018) and estimated from 23 clusters.
- Screening bias: the original run kept only problems with 0 < p(success) < 1 on 6 screening
  rollouts, inflating Var(p) relative to unscreened GSM8K; pooled lambda ~ 1.15 is therefore
  optimistic for an unscreened population (within-problem lambda is less affected).
- Finite pool: each draw splits the same 18 saved outcomes; the B-averaged r estimates the
  expected disjoint-split correlation, which equals the fresh-rollout quantity under
  exchangeability, but all draws reuse the same 18 outcomes per prefix.
- One model (1.5B, 4-bit), one dataset (GSM8K), one original run, unseeded generation upstream.
- Discovered in passing: the README describes the simulator/gold as 8/16 rollouts, but the saved
  full run used 6/12 (script defaults changed or overridden); all analysis here uses the actual
  6/12 counts verified from the saved fractions and log.
